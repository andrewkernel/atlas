# Phased implementation plan

Effort ranges below are **developer effort estimates**, not delivery dates or measured durations. Core phases1–3 plus the required part of 5 target roughly 10–16 focused developer weeks after research, with substantial uncertainty. Optional LLM/UI/dissemination work adds effort and should be removed if it delays the primary experiment. A student working part-time will take longer in calendar time.

## Order and dependencies

Phase4 can follow3 but is not a dependency of 5. Phase6 is not a dependency of any research result. The required path is 0→1→2→3→5→7. Do not implement distributed execution, arbitrary AST patches, hosted services, PostgreSQL or a custom optimizer before the primary comparison.

## Work ownership for one developer

Keep issue-sized tasks to one observable result. Every task names a contract, a failure behavior and an evidence artifact. Integration tests must exercise a complete logical update rather than mock all scientific computation. Use tiny CPU fixtures in ordinary CI and explicit optional CUDA tests; full training is a controlled experiment, not every-commit CI.

## Release gates

The first useful release is a profiler/report tool, not an optimizer. The research MVP follows after two strategies and meaningful negative controls. A public scientific-preservation claim requires the relevant repeated study and domain review, not the existence of the report UI. Revisit the [ADRs](../research/decisions/README.md) whenever scope or evidence obligations change.
