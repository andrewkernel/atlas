# Frozen Windows job-boundary lifecycle control

Follow the launcher-ownership diagnostic with a separate authored process-management control. Do not modify or rerun the historical QA supervisor. Use the existing QA interpreter and a bounded stdlib child that rendezvous before allocation, then touches 64 MiB after acknowledgment. The controller uses the core environment's psutil and an authored ctypes wrapper around documented Windows job APIs.

Discover the actual interpreter in the owned launcher's descendants, retain PID/creation identity, and verify the opened process handle's creation time before job assignment. Assign both existing launcher and actual interpreter to a new unnamed non-inherited job with KILL_ON_JOB_CLOSE and no breakaway flags. Require both PIDs in the queried job inventory before acknowledgment. Assignment or identity failure must abort, with cleanup of observed owned identities; no privilege escalation or job-policy change. This is a trusted rendezvous, not security against pre-handshake hostile code.

Three intended cases: natural exit, explicit TerminateJobObject(code=42), and closing the last job handle while the child waits. Verify cleanup of both retained identities before the next case. For each, test deliberate wrong creation identity before correct assignment, record rejection, and record launcher versus actual RSS plus job commit accounting after allocation. Reject use after close. Parent deadline is ten seconds; child waits at most five seconds for acknowledgment and at most two seconds after allocation. No training, CUDA or foreign source executes.

Job commit accounting, working set and GPU allocation have different scopes. This control sets no hard memory limit. Future training guards must monitor the correct boundary and stop the job; success here does not validate every memory-pressure, parent-crash, descendant-spawn or startup-error path. A production supervisor needs those additional controls. Job objects are process-lifecycle infrastructure, not a hostile-code sandbox.

Primary API sources inspected: [assignment and nested-job restrictions](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [extended limit/accounting fields](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information), [basic limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information), [job lifecycle](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). No application privilege or GPU driver setting is changed.
